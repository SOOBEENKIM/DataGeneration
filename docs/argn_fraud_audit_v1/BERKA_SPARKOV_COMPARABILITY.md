# Berka 재현과 이전 Sparkov 감사는 같은 실험이 아니다

2026-09-27. 이 표는 결과의 해석 범위를 고정한다. 차이를 발견했다는 것과 그 차이가 성능 저하의 원인임을 입증한 것은 다르다.

| 항목 | 이번 Berka 재현 | 이전 라벨 포함 Sparkov 감사 |
| --- | --- | --- |
| 자료 | 저자 저장소의 원본 Berka account/transaction train | 사용자 Sparkov의 개발 분할 |
| 학습에 전달한 고객 수 | 2,250 | 내부 fit 550 / check 138 |
| engine | 1.0.4, 논문 v2 발표 시점 배포 | 2.4.0 |
| 정적 고객 정보 | 별도 부모 모델을 학습하고 합성 부모 생성 | 실제 validation 고객의 정적 정보 제공 |
| 자식 생성 조건 | 합성 부모 2,250개 | 실제 validation 고객 147개 |
| 시간 필드 | 공개 CSV 날짜 문자열 그대로, 범주형 | 연구용 거래 간격으로 변환 |
| 사기 라벨 | 없음 | `event_is_fraud`를 다른 거래 필드와 함께 생성 |
| 내부 분할 | native 90/10, 계좌 단위 | 기존 역할표 fit/check 사용 |
| codec 분석 | native analyze, 내부 train/validation | fit만으로 분석하는 별도 처리 |
| 학습 배치 | native 자동 결정 16 | 명시한 64 |
| 최대 sequence window | native 기본값 100 | 명시한 100 |
| 최대 epoch / 시간 | 기본 100 / 테이블당 300분 | 100 / 30분 |
| 모델 선택 | native 검증·조기 종료 | native 검증·조기 종료 |
| 대표 평가 | QA 1.5.3의 구간화된 저차 분포 점수 | 가맹점–유형 전체 범주 공동분포, 사기 조건별 관계 등 |

숫자 `overall accuracy .79`는 사기탐지 정확도나 merchant→category 분류 정확도와 다르다. 희귀 범주를 합치고 변수를 평균내는 분포 점수 하나만으로 고객별 모든 관계가 보존됐다고 판단하지 않는다. 반대로 세부 관계 오류 하나만으로 원문 전체 benchmark가 재현되지 않는다고 판정하지 않는다.

다음 Sparkov 기준 실험은 Berka 실행의 성공 여부와 평가 범위를 먼저 기록한 뒤, 고정한 공식 버전·부모→자식 절차·기본 학습 설정을 적용하는 단계다. Sparkov용 의미 있는 필드 처리(특히 고객 속성과 거래 간격, 라벨)는 데이터가 달라 필요한 변경이므로 명시적으로 남긴다. 이 대조가 완료되기 전에는 ‘Berka와 똑같이 하면 Sparkov에서는 실패한다’고 결론내리지 않는다.
