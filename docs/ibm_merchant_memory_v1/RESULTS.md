## 3. 판정

- **H1 채택(`full`).** 새 가맹점 비율 사기 1.1배·정상 일치(.078 vs .084), 공유 사기 가맹점 1.8배, 고객당 가맹점 수 66.9배 → 2.4배. `gate_only`는
  공유 풀 4.1배로 H1의 그 항목 미달 — 풀이 그 구조를 담당한다.
- **H2 채택.** ARGN 효용 .142 → **.306**(`full`) / **.320**(`gate_only`), 기준 .25 초과(State-First M3의 "강" 기준 .30도 충족). 상한 대비 .50.
  경로: TSTR 특징 `seen_merchant`·`seen_merchants_5`가 정상(반복)·사기(새로움)를 가르게 됐다 — `repeat_blind`(정상·사기 모두 .08)는 효용이
  오르지 않는 것(.133)이 그 증거.
- **H3 채택(구조), 효용은 부분.** 사기 새 가맹점 절대차 `full` 1.1 < `gate_only` 1.7 < `repeat_blind` 20.6. 효용은 `full` ≈ `gate_only`(.306 vs .320,
  차이는 fit 분산 안) — 탐지기가 가맹점 **정체**를 쓰지 않으므로 풀은 효용에 기여하지 않는다. 즉 **상태 조건부 게이트가 효용을 올리는 부품**,
  풀은 충실도(공유 구조) 부품. `repeat_blind` ≈ 현재 모델(.133 vs .142): 습관만 복원하고 사기 새로움을 안 주면 아무 이득이 없다.
- **H4 위반 1건(기록).** 라벨 과정 지표·사기 고객·금액 분포는 불변이고 업종 TV는 .186 → .120으로 **개선**(업종이 가맹점 뒤에 생성되어 실제
  가맹점에 조건부가 됨)되었으나, **표준 간격 log-W1이 .113 → .188(+.075)** 로 등록 기준(≤ .01)을 넘었다(바닥 배 1.4 → 2.4, 3배 잡음 안).
  원인: 간격 열은 같은 행에서 가맹점보다 먼저 나오지만 LSTM 이력이 가맹점 임베딩을 받으므로 다음 행부터 모든 열이 가맹점의 하류다.
  등록 기준을 소급 변경하지 않는다 — **등록 기준으로는 간격 항목 위반**이며, 그 크기는 바닥 잡음 범위(2.4배)임을 함께 기록한다. 수정안 1(아래).
- **H5 미실행.** ARGN H1 충족이므로 프로토콜대로 RTF `rtf_full`(LogitsProcessor 구현)이 다음이다.

## 4. 결정

State-First Generator에 **세 번째 부품 "이력 참조 가맹점 생성"(상태 조건부 반복/새로움 게이트 + 고객 과거 포인터 + 사기 공유 풀)** 을 추가한다.
ARGN 효용 .14 → .31(상한의 절반), 가맹점 축 67배 → 2.4배, 라벨 과정·정상 금액 불변. 부품은 데이터 구조(.08 / .55 / .74)에서 유도됐고
파라미터가 모두 읽을 수 있는 표·비율이다. 설명 가능한 ablation: 게이트(효용) / 포인터(습관) / 풀(공유 구조) 각각의 역할이 분리된다.

## 수정안 1 — H4 간격 기준 (2026-11-09, 결과 후; 소급 아님)

등록 시 "가맹점 무관 표준 지표 변화 ≤ .01"을 두었으나 순차 모델에서 가맹점 **무관** 열은 같은 행의 상류 열뿐이고 다음 행부터는 전부 하류다.
이후 단계의 H4는 "라벨 과정 지표 불변 + 모든 표준 지표 바닥 배 ≤ 3"으로 쓴다. 이번 결과의 간격 +.075는 그 기준으로는 통과(2.4배)이나,
이 단계의 공식 판정은 등록 기준대로 "H4 위반 1건"으로 남긴다.

## 6. H5 — RTF `rtf_full` (2026-11-10)

구현 `benchmarks/rtf_merchant_memory.py`: 가맹점 토큰 위치(열 5, 라벨 뒤)의 LogitsProcessor. 게이트·λ·π는 ARGN 추정과 **동일**(RTF 어휘로 재추정해
일치 확인 `merchant_memory_rtf.json`; 풀 191개를 가맹점 토큰으로 색인). 고객 과거 = 이전 창에서 이월한 가맹점별 횟수·마지막 위치(전이 상태처럼
이월) + 현재 창에서 이미 생성된 가맹점 토큰. RTF는 가맹점 25,088개가 각각 토큰이라 `_RARE_`가 없다. 새로움 가지 = 과거 마스크 후 backbone
top-50 디코딩(원형의 top-k 규칙을 미방문 가맹점에 한정). HF의 top-k=50 warper가 사용자 processor **뒤**에 걸려 혼합을 잘라내므로 `top_k=0`으로
부르고 비가맹점 위치에는 processor 안에서 동일한 top-k 필터를 건다(`check_mm`: warper와 일치, 모든 가맹점 위치 대체, 2번째 창 게이트 .527 =
표의 5–19 구간 값, 이월 재집계 일치). 생성 4(fit 2 × seed 2, 각 ~27분 — 원형과 같은 속도). 라벨 과정은 `rtf_table`과 동일(사기 566/298행, 37/24명,
지속률 .657/.634).

해석(기록, 추가 실험으로 확인 필요): RTF 원형은 **정상 행의 습관 구조를 이미 갖고 있었다**(새 가맹점 .069 ≈ 실제 .08, 고객당 가맹점 수 상대차 .19).
문제는 사기 행(.21)뿐이었는데 `rtf_full`은 모든 행의 가맹점을 표·커널로 대체했다 — backbone이 창 맥락에 조건부로 내던 가맹점 토큰을 빈도/최근성
커널이 고른 토큰으로 바꾸면 그 토큰에 강하게 조건부인 이후 토큰(금액·업종·다음 행 간격)이 학습 분포 밖으로 밀리고, 정상 행 분포의 드리프트가 효용을
깎는다(TSTR 탐지기는 간격·금액 특징도 쓴다). ARGN은 LSTM 이력이 9,411 코드 임베딩을 받는 정도라 같은 대체의 하류 영향이 작았다. 즉 이 부품은
구현한 형태로는 **backbone 불문이 아니다**: "무엇이 빠졌는가"(ARGN: 습관·새로움 둘 다 / RTF: 사기 새로움만)에 맞춰 개입 범위를 정해야 한다.

## 수정안 2 — RTF 원인 특정 ablation `rtf_fraud_only` (2026-11-10, §6 결과 후 등록; 실행 전)

- 팔: `rtf_fraud_only` = 사기 행의 가맹점 위치에서만 게이트·포인터·풀을 적용하고 **정상 행은 원형 그대로**(top-k 포함). 과거 추적은 모든 행.
  나머지(전이표, fit 2 × seed 2, 평가 3종)는 `rtf_full`과 같다. 생성 4(~1시간, GPU 2개).
- 가설 A2-1: 정상 행을 건드리지 않으면 표준 간격·금액·업종·사기 온라인 비율이 `rtf_table` 수준(±바닥 1배)으로 돌아온다 — "정상 행 대체가 드리프트의
  원인"의 확인. A2-2: 사기 새 가맹점이 바닥 3배 안으로 들어오고(생성 .45–.60), 효용이 `rtf_table`(.448) 이상이면 "RTF에서는 사기 행 한정 개입이 맞는
  형태"로 채택; 효용이 .448 미만이면 "RTF에서 가맹점 새로움은 효용 경로가 아님"으로 기록하고 RTF 채택 안 함. 어느 쪽이든 H5 공식 판정은 미달로 남긴다.
- 하지 않는 것: RTF 재학습, 게이트 표 재추정, ARGN 쪽 재실행.

**RTF에는 채택하지 않는다**. H5 공식 판정은 미달로 유지.

왜 ARGN에서는 +.16이고 RTF에서는 −.06인가(기록; 추가 실험 없이 데이터로 보이는 범위): (i) ARGN은 습관(정상 .33)과 사기 새로움(.34) **둘 다** 없어서
부품이 탐지기 특징 `seen_merchant`의 정상/사기 대비를 새로 만들었다. RTF는 습관(.069)이 이미 있었고 사기 새로움만 .21 → .59로 올랐는데 이것은 효용을
올리지 않았다. (ii) 대신 사기 행의 **온라인 비율이 .85 → .72**(실제 .88)로 떨어졌다: RTF는 `use_chip`을 가맹점 토큰에 조건부로 내는데, 풀 가맹점(191개,
train에 평균 7행)은 조건부 학습이 약해 정상 행의 채널 사전분포로 돌아간다. 등록 탐지기에 채널 특징이 있어 이 손실이 새로움 이득을 상쇄했을 수 있다.
(iii) 즉 이 부품의 효용 효과는 "그 backbone에 빠진 가맹점 구조가 탐지기 특징과 맞물리는가"에 달렸고, backbone 불문 주장은 **할 수 없다**.

결론(모델): 이력 참조 가맹점 생성은 **ARGN 위 State-First Generator의 부품**으로만 채택한다(ARGN: 구조 복구 + 효용 .14 → .31). RTF 위에서는 구조만
복구하고 효용은 내리므로 넣지 않는다. 전이표 상태 과정(두 backbone 모두 효용 상승)과 구분해 쓴다.

## 수정안 3 — 효용 상승의 탐지기 의존성 확인 (2026-11-10 등록, 실행 전; 사용자 "두 번째 탐지기 시작")

질문: ARGN 효용 .142 → .306이 등록 탐지기의 가맹점 반복 특징(`seen_merchant`, `seen_merchants_5`)에만 기대는가, 그리고 §7의 RTF 효용 하락이 채널
드리프트로 설명되는가. 새 fit·새 생성 0, 기존 144 생성 + 실제 기준(train 부분표본 20, dev 자기 자신)을 다시 채점한다. 평가는 dev만, 봉인 test 미읽음.

| 변형 | 분류기 | 특징 | 보는 것 |
|---|---|---|---|
| 기준(기존) | `stable` HGB | 전체 | — |
| `no_merchant` | `stable` HGB | `seen_merchant`·`seen_merchants_5` 제거 | D1 |
| `no_channel` | `stable` HGB | `chan_*` 제거 | D2 |
| `logistic` | 표준화 + 로지스틱 회귀(C = 1, max_iter 500) | 전체 | D3 |

사전 판단(효용 = history AUPRC, fit 2 × 생성 2 평균; 각 변형의 실제 상한을 함께 보고):
- **D1.** ARGN `full` − 현재 모델(`routed_subst_table`) 차이가 `no_merchant`에서 < .03이면 "상승은 전적으로 가맹점 반복 특징 경유(탐지기 의존)"로,
  ≥ .08(기준 차이 .16의 절반)이면 "다른 경로도 있음"으로, 그 사이면 "대부분 가맹점 특징 경유"로 적는다. `repeat_blind` 대비도 함께.
- **D2.** `no_channel`에서 `rtf_fraud_only` − `rtf_table` 차이가 −.06에서 ≥ −.02로 줄면 "RTF 효용 하락은 채널 드리프트로 설명됨", 아니면 "설명 안 됨"
  으로 §7 해석 (ii)를 고친다.
- **D3.** `logistic`에서 ARGN `full` − 현재 모델 ≥ .05(또는 그 변형 상한의 1/4 이상)이면 "분류기 계열을 바꿔도 유지", 아니면 "HGB 한정"으로 적는다.
- 어느 결과든 ARGN 부품 채택 결정(구조 복구 H1)은 그대로이고, 바뀌는 것은 **효용 주장의 범위**다. 변형 탐지기는 보조 지표이며 등록 탐지기를 대체하지 않는다.
