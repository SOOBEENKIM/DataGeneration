## 1. 무엇을 어디에 넣는가

- **머무름(생성기 안).** 가맹점을 정하는 단계에서, 정상 행이고 직전 행도 정상이면 "이미 가 본 가맹점을 고르는 몫" 안에서 **직전 가맹점**의 확률을 그 행의 간격 구간별 train 값(1분 이하 .79 … 1시간 이상 .05–.09)으로 맞춘다.
  새 가맹점을 고르는 몫과 사기 행은 건드리지 않는다. 생성 순서가 라벨 → 간격 → 가맹점이므로 간격을 조건으로 쓸 수 있다. 머무른 행의 업종·채널은 기존 속성 규칙이 가맹점에서 정한다.
  후처리 모의와 달리 이후 행의 생성(가맹점 방문 횟수, backbone의 이력)이 이 선택을 보고 이어진다.
- **금액(디코딩 단계).** 엔진 안에서 금액은 100개 구간의 부호일 뿐이고 실제 값은 생성이 끝난 뒤 구간 안에서 균등하게 뽑힌다(마지막 구간은 316–2,801로 넓다). 그래서 정확한 금액은 디코딩 단계에서만 정할 수 있다.
  정상 행(금액 > 0)의 금액을 엔진의 균등 추출 대신 `AMT3`(업종 평균 + 고객의 그 업종 지난 금액 평균으로의 회귀 + 잔차, 업종별 고정 단조 함수)로 정한다 — 모의에서 검증한 그대로의 표·함수(`tables_v2.json`, `tables_v3.json`)다.
  사기 행의 금액은 엔진이 낸 그대로다. 한계: backbone은 보정된 금액 이력을 보지 못한다(모의에서 사기 금액의 기준 재설정이 효용에 영향이 없음을 확인했다).

## 2. 생성과 팔

평가 틀의 수정안대로 **생성 seed를 fit마다 다르게** 한다: fit 2개 × seed 4개 = 독립 생성 8개(seed = 20261100 + 10·i + j). dev 문맥. GPU가 다른 사용자의 작업으로 차 있으면 CPU로 생성한다(다른 작업은 건드리지 않는다).

| 팔 | 구성 |
|---|---|
| `B` | 채택 모델(같은 새 seed로 다시 생성) |
| `R` | `B` + 머무름(생성기 안) |
| `BA` | `B`의 생성물 + 금액 디코딩 단계 |
| **`RA`** | `R`의 생성물 + 금액 디코딩 단계 (구현 대상) |

## 3. 판정 (dev, 수치 고정)

- **I1 (구조가 생성기 안에서도 서는가).** `RA`에서: 간격 10분 미만 정상 행의 "직전과 같은 가맹점" ≥ .55(실제 .74, 모의 .68); 업종별 평균 금액의 표준편차 ≥ .60(실제 .75); (고객, 업종) 안 금액 표준편차가 실제(1.011)의 ± .10;
  고객당 가맹점 수 dev 바닥의 3배 안; 정상 행 속성 일관성 ≥ .99; 라벨 과정(사기율·지속률·구간 길이)이 `B`와 같은 범위(각 지표의 `B` 대비 차이 ≤ 1배).
- **I2 (효용이 재현되는가).** 등록 탐지기, 생성 8개 평균. `RA` − `B` ≥ **+.02**이면 "재현", 0 ~ +.02이면 "부분 재현", 0 이하면 "미재현". 평균 차이의 표준오차(독립 8 대 8)를 함께 적는다.
  짝지은 대조도 본다: `RA` − `R`(금액 단계의 효과), `BA` − `B`.
- **I3 (충실도).** `RA`의 표준 지표 최댓값 ≤ 3배(모의 1.58), 정상 행 판별기 AUC가 `B`보다 .05 이상 낮음, 사기 구조(새 가맹점·구간 내 간격·진입 금액비) ≤ 3배.
- I1·I3을 충족하고 I2가 "재현"이면 v2의 정상 행 부품으로 채택한다. I2가 "부분 재현"이면 충실도 부품으로만 기록하고 채택 여부는 사용자가 정한다. I1 또는 I3 미달이면 채택하지 않는다.

## 4. 한계(미리 적음)

- dev는 설계·모의·판정에 모두 쓰였다. 여기의 수치는 구현이 모의와 같은지의 확인이며, 확인 평가는 봉인된 연도에서 한다.
- 독립 8 대 8로는 +.02 안팎의 차이를 겨우 가른다(생성 간 표준편차 약 .03). 부족하면 seed를 더하는 수정안을 실행 전에 등록한다.
- 머무름을 생성기 안에 넣으면 이후 행의 생성이 달라진다. 후처리 모의의 수치가 그대로 나온다는 보장은 없다 — 그것을 재는 것이 이 단계다.
